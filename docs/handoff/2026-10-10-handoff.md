## 4. O que existe da plataforma de parceiros

### Níveis e rotas

| Nível              | Rota        | Quem                                                                                                    |
| ------------------ | ----------- | ------------------------------------------------------------------------------------------------------- |
| Plataforma (GUIDU) | `/platform` | Papéis internos (`owner`, `operations`, `billing`, `support`); só em host da plataforma, 404 nos demais |
| Parceiro           | `/admin`    | `partner_owner`, `partner_admin`, `partner_finance`, `partner_support`; exige AAL2                      |
| Cliente (empresa)  | `/app`      | Membros de empresa e workspace                                                                          |

- **Parceiro zero (da casa):** `00000000-0000-4000-8000-000000000000` (`HOUSE_PARTNER_ID` em `src/core/partners/constants.ts`).
- **Resolução por host** (`src/core/partners/hosts.ts`, `resolve.ts`):
  - hosts da plataforma vêm de `APP_URL`, `PLATFORM_HOSTS` e, fora de produção, `localhost`/`127.0.0.1`; sempre resolvem para o parceiro zero;
  - os demais hosts saem de `partner_domains` (ativos) por `resolve_partner_host()`;
  - o host é lido por `requestHost()`: **primeiro `X-Forwarded-Host`, depois `Host`**. Motivo: depois de `redirect()` em Server Action o Next renderiza o destino por uma requisição interna em que `Host` é o servidor;
  - subdomínio de plataforma: o parceiro informa só o nome; o host vira `nome.PARTNER_SUBDOMAIN_BASE` (padrão `localhost` fora de produção). Em dev, use `agencia.localhost:3000`.
- **Contexto no banco:** `withIdentityContext(prisma, userId, fn, { partnerId })` e `withPartnerContext` definem as GUCs `app.*`, incluindo `app.partner_id`. Helpers SQL: `private.current_partner_id()`, `private.current_partner_role()`, `private.is_partner_organization()`, `private.can_manage_partner_customers()`, `private.support_grant_valid()`.
- **Empresas e workspaces:** `organizations.partner_id` é obrigatório e não muda pela aplicação (gatilho). `resolve_workspace_slug` e `list_user_workspaces` exigem o parceiro do contexto; páginas usam `resolveRequestWorkspaceContext` e `listRequestUserWorkspaces` (`src/core/partners/request-context.ts`).

## 5. Armadilhas já encontradas

Cada uma custou um ciclo de CI ou um bug. Releia antes de escrever migration.

1. **Migration roda como `app_migrations`** (NOINHERIT, NOBYPASSRLS):
   - semear linhas **antes** de ligar RLS com FORCE;
   - dar `grant` nas funções **antes** de `alter function ... owner to app_rls_helper`;
   - para trocar função de `app_rls_helper`, usar `set local role app_rls_helper; create or replace ...; reset role;`.
2. **Supabase dá privilégios padrão a `anon` e `authenticated`** em toda tabela nova de `public`. Toda tabela nova precisa de `revoke all on ... from public, anon, authenticated;`. O teste `tests/core/invariants.sql` pega a falta.
3. **Políticas `UPDATE` permissivas se combinam:** o `USING` de uma vale com o `WITH CHECK` de outra. Todo `WITH CHECK` repete quem pode escrever (foi assim que o solicitante conseguia aprovar o próprio pedido de suporte).
4. **Prisma raw com várias instruções** falha: um `$executeRawUnsafe` por instrução. Inserts sob RLS sem política de `SELECT` não podem usar `RETURNING` (por isso `createPartnerCustomer` usa inserts crus sem retorno).
5. **Auditoria tem FK para empresas:** testes não apagam empresas; devolvem ao parceiro zero na limpeza.
6. **`headers()` fora do `try`** nas leituras de marca, senão o Next perde o sinal de página dinâmica.
7. **E2E:** o Node não resolve `*.localhost`; no Playwright use fetch dentro da página. Locators ambíguos quebram: use `exact` ou escopo.
8. **Prettier:** formate só arquivos que estavam limpos em `HEAD`; vários arquivos antigos não seguem o Prettier e reformatá-los polui o diff.
9. **Testes de mutação:** ao alterar função no banco local para provar que um teste SQL morde, recrie o banco depois.
