# Análise do documento de visão do Guidu.chat

- **Status:** análise para discussão.
- **Data:** 23/10/2026
- **Documento analisado:** [Guidu.chat: visão de produto, arquitetura e casos de uso v1.0](../spec/guidu-chat-visao-produto-v1.0.md) (21/10/2026)
- **Comparado com:** ADRs, [commerce do guidu.chat](commerce-guidu-chat.md), [ponte dos mini-apps](mini-apps-bridge.md), [gateways](gateways.md) e o código da `main`.

## 1. Resumo

O documento é a melhor fonte que temos sobre o **guidu.chat do lado do turista**: jornadas, casos de uso, piloto, app nativo, mini-apps e a Mini App Bridge. Quase tudo pode ser aproveitado. Ele tem três tipos de conteúdo:

1. **Coisas novas para o projeto**, que preenchem lacunas dos nossos documentos (seção 2).
2. **Perguntas que ele deixa abertas e o projeto já respondeu** (seção 3).
3. **Pontos que divergem** do que está decidido ou implementado (seção 4).

O próprio documento diz que é proposta, não auditoria do código.

## 3. Perguntas do documento que o projeto já respondeu

| Pergunta do documento (12.4)                                        | Resposta no projeto                                                                                                                                                                                                 |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Qual homeserver Matrix e qual política de E2EE?                     | Synapse único e fechado, **sem E2EE**, porque o agente, a tradução e a auditoria leem as mensagens (ADR 0023, regras 2 e 3). Isso atende à seção 8.4 do documento: declarar onde o conteúdo é lido                  |
| Tradução por participante, original preservado                      | Feito: TR1 a TR3 ([traducao.md](../modules/inbox/traducao.md)); tradução fica no Supabase, nunca na sala do lead                                                                                                    |
| BYOK e agentes                                                      | Feito: chave do dono por turno, chave reserva, Painel de IA (ADR 0017, 0019, CF6a); agente principal e subagentes = orquestrador, atendente e vendedor (GF1 e GF2)                                                  |
| Conversa ↔ sala idempotente                                         | Feito na IN7a: uma sala por pessoa e loja, reaproveitada                                                                                                                                                            |
| Quais eventos entram na sala e quais ficam nos serviços comerciais? | Regra já escrita: a sala leva só o id do registro; preço, carrinho e pedido ficam no banco ([compra agêntica](agentes-na-matrix-e-compra-agentica.md), §2.2), agora no Vendure ([commerce](commerce-guidu-chat.md)) |
| WhatsApp                                                            | Adaptador Meta Cloud API no núcleo (ADR 0023, regra 11)                                                                                                                                                             |

## 4. Divergências a resolver

| #   | Documento                                           | Projeto                                                                                                        | Proposta                                                                                                                                                                                    |
| --- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | "Portfólio com fotos, textos e QR: existente"       | O Portfólio deste repositório não tem QR (`src/modules/portfolio`)                                             | Conferir se o QR existe em outro repositório (o `console-guidu` original ou o legado). Se não, entra no módulo Mini Apps (A9)                                                               |
| D2  | `Order Service` próprio                             | Vendure como motor de pedido ([commerce](commerce-guidu-chat.md))                                              | Mantém o Vendure; o `Order Service` do documento passa a ser o Vendure, e a `CommercialRequest` (A3) fica no GUIDU antes dele                                                               |
| D3  | Identidade "OIDC/OAuth 2.1 com PKCE" para o turista | ADR 0009 (MCP por chaves, OAuth do Supabase descartado para o MCP); login Matrix por JWT do console (ADR 0023) | Para o turista, OIDC com PKCE no app nativo faz sentido. Decidir junto com a pergunta 4 do commerce (projeto Supabase do turista). Não muda a ADR 0009, que é do MCP                        |
| D4  | Monorepo com `apps/` e `packages/`                  | Repositório único Next.js; kit em repositório separado (`guiduchat-ui`)                                        | Não migrar para monorepo agora. Runtime dos mini-apps começa como host próprio servido pelo console; `miniapp-sdk` e `miniapp-contracts` como pacotes pequenos ao lado do `guiduchat-ui`    |
| D5  | Mini-apps "publicados pelos comerciantes"           | A ponte proposta tinha um catálogo de mini-apps da plataforma                                                  | Os dois juntos: o **código** (templates) é da plataforma; o comerciante publica **instâncias** (template + conteúdo + QR). Nenhum comerciante sobe código próprio, e a origem continua fixa |
| D6  | `merchantId`                                        | Workspace (loja) dentro de uma empresa e, às vezes, de um parceiro                                             | `merchantId` = `workspace_id`; o vendedor do Vendure segue o mesmo mapa                                                                                                                     |
